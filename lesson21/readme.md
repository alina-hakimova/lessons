# DevOps Pet Project — Полный цикл DevOps и микросервисная архитектура
Этот проект предназначен для практики полного цикла DevOps и микросервисной архитектуры. 
## 📦 Структура проекта
```
.
├── dev
│   └── service_py
├── nginx
│   └── nginx.conf
├── ports_config.txt
├── service-go
│   ├── Dockerfile
│   ├── main.go
│   ├── main_test.go
│   └── service-go
├── service_py
│   ├── app.py
│   ├── Dockerfile
│   └── test_app.py
├── stage
│   └── service_py
└── systemd
├── service-go-app4.service
└── service-py-app3.service

```
## 🧩 Сервисы

Бизнес-логика построена на двух сервисах, каждый — модуль со своей зоной ответственности:

- **Service-Py — Заказы (Orders):**  
  Отвечает за создание, хранение и управление жизненным циклом заказов. Предоставляет API для работы с заказами: создание, получение, обновление, отмена.

- **Service-Go — Отгрузки (Shipments):**  
  Обрабатывает процессы отгрузки заказов клиентам, регистрирует статусы доставки, интегрирует подтверждения и возвраты. Поддерживает смену статуса и просмотр информации по отправлениям.

Оба сервиса независимы и могут масштабироваться отдельно.

---

## ⚡ Варианты развертывания

Каждый сервис разворачивается двумя способами:

- **Docker-контейнер:** быстрое развертывание и изоляция среды  
- **systemd-сервис:** традиционное управление ОС без контейнеризации

В итоге разворачиваются 4 приложения:

| Приложение | Сервис       | Способ запуска |
|------------|--------------|---------------|
| app1       | Service-Py   | Docker        |
| app2       | Service-Go   | Docker        |
| app3       | Service-Py   | systemd       |
| app4       | Service-Go   | systemd       |

---

## 🌐 Внешний доступ через Nginx

Для всех четырёх приложений настроен обратный прокси с маршрутизацией по path-префиксу:

- `http://<vm>/app1/` → Service-Py (Docker)  
- `http://<vm>/app2/` → Service-Go (Docker)  
- `http://<vm>/app3/` → Service-Py (systemd)  
- `http://<vm>/app4/` → Service-Go (systemd)  

---

## 🏷️ Версионирование

Каждый сервис реализует эндпоинт `/version`, возвращающий текущую версию git-сборки в формате JSON:

```

{ "version": "git-a1b2c3d" }

```

Это позволяет быстро идентифицировать состояние сервиса для диагностики и откатов.

---

## 🔄 CI/CD (GitLab)

Автоматизация сборки и деплоя через GitLab CI:

- `.gitlab-ci.yml` содержит пайплайны для Docker-контейнеров и бинарников для systemd  
- Есть 4 независимых пайплайна деплоя, каждый отвечает за конкретный экземпляр сервиса  
- Пайплайны выполняют:  
  - Сборку по коммиту,  
  - Тесты,  
  - Деплой через SSH/Docker,  
  - Перезапуск systemd-сервисов по необходимости.

## ✅ Acceptance Criteria

Проект считается выполненным, если выполнены условия:

- Реализованы оба сервиса: Service-Py (заказы) и Service-Go (отгрузки)  
- Запущено по 2 экземпляра каждого сервиса (Docker и systemd)  
- Nginx маршрутизирует запросы на все 4 экземпляра  
- Все сервисы поддерживают ручку `/version` для возврата версии  
- В репозитории есть `.gitlab-ci.yml` с 4 пайплайнами деплоя  
- После развертывания проходят проверки командой:

```

curl http://<vm>/app1/version
curl http://<vm>/app2/version
curl http://<vm>/app3/version
curl http://<vm>/app4/version

```

- Чёткое разделение бизнес-логики и инфраструктуры
