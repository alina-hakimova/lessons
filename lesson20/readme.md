
Этот проект предназначен для практики полного цикла DevOps и микросервисной архитектуры. Задача: пройти путь от разработки бизнес-логики до деплоя и развертывания сервисов разными способами (Docker, systemd), автоматизировать доставку через CI/CD, обеспечить внешний доступ через Nginx, а также внедрить версионирование на уровне приложения.[^1]

Все реализации, скрипты и конфигурации размещены в репозитории:
[https://github.com/alina-hakimova/lessons.git](https://github.com/alina-hakimova/lessons.git) (ветка lesson20).

***

## 🧩 Сервисы

Бизнес-логика построена на двух сервисах, каждый — модуль со своей зоной ответственности:

- **Service-Py — Заказы (Orders):**
Реализует создание заказа, хранит его данные, управляет жизненным циклом заказа (создание, получение, обновление, отмена). Выполняет обработку входящих заказов и предоставляет API для работы с ними.
Пример: клиент оформляет заказ; сервис создает запись, возвращает ее по запросу, и позволяет менять статус заказа.
- **Service-Go — Отгрузки (Shipments):**
Этот сервис отвечает за обработку процессов отгрузки: регистрирует факт отправки заказа клиенту, фиксирует статусы доставки, интегрирует подтверждение или возврат отправления. API поддерживает смену статуса отгрузки и просмотр информации по отправкам.[^3]

Оба сервиса используют подход слабо-связанных компонентов: операции сервисов не зависят от внутренних деталей реализации друг друга и могут масштабироваться независимо.[^3][^2]

## ⚡ Варианты развертывания

Для повышения гибкости и демонстрации DevOps-решений каждый сервис разворачивается двумя способами:

- **В Docker-контейнере:**
Быстрая установка, изоляция среды и легкая миграция между машинами.
- **Как systemd-сервис (без Docker):**
Традиционное управление сервисом ОС, позволяет плотно интегрировать с серверной инфраструктурой и дополнительными инструментами мониторинга.

В итоге разворачиваются 4 приложения:

- app1 → Service-Py (Docker)
- app2 → Service-Go (Docker)
- app3 → Service-Py (systemd)
- app4 → Service-Go (systemd)

***

## 🌐 Внешний доступ через Nginx

Для всех 4 экземпляров настраивается обратное прокси:

- http://<vm>/app1/ → Service-Py (Docker)
- http://<vm>/app2/ → Service-Go (Docker)
- http://<vm>/app3/ → Service-Py (systemd)
- http://<vm>/app4/ → Service-Go (systemd)

Доступ обеспечивается централизованно через Nginx, маршрутизация происходит по path-префиксу.

***

## 🏷️ Версионирование

У каждого микросервиса реализована ручка /version, возвращающая JSON-объект с git-версией сборки:

```json
{ "version": "git-a1b2c3d" }
```

Позволяет точно идентифицировать релиз, удобно для диагностики и отката.

***

## 🔄 CI/CD (GitLab)

Автоматизация происходит через GitLab CI:

- В .gitlab-ci.yml реализована сборка для Docker-контейнеров и обычных бинарников (systemd-варианты).
- Есть 4 независимых пайплайна деплоя — каждый деплоит конкретный экземпляр сервиса на виртуальную машину.

Пайплайны обеспечивают:

- Сборку приложения по коммиту,
- Деплой через ssh/scp или Docker,
- Перезапуск systemd-сервиса (если нужно),
- Готовность сервиса к работе без ручных действий.

## ✅ Acceptance Criteria

Проект считается выполненным, если:

- Реализованы оба сервиса: Service-Py (заказы) и Service-Go (отгрузки).
- Запущено по 2 экземпляра каждого сервиса (Docker/systemd).
- Nginx маршрутизирует все 4 пути для внешнего доступа.
- Все сервисы поддерживают возврат своей версии по /version.
- В репозитории есть .gitlab-ci.yml с 4 отдельными пайплайнами деплоя.
- После развертывания проходят проверки:

```
curl http://<vm>/app1/version
curl http://<vm>/app2/version
curl http://<vm>/app3/version
curl http://<vm>/app4/version
```


***

## 💡 Архитектурные принципы

- Сервисы реализованы как независимые компоненты с четкой бизнес-логикой (слой service отделен от инфраструктурных деталей).
- Разделение развертывания (Docker/systemd) демонстрирует гибкость DevOps-подхода.
- Nginx обеспечивает централизованный маршрутизатор запросов.
- Версионирование позволяет отслеживать релизы на каждом экземпляре.
- Автоматизация CI/CD исключает ручные процессы от коммита до продакшн.
